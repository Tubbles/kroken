## Project kickoff decisions

- **Language and toolchain**: Odin, pinned to release `dev-2026-09` via `scripts/setup-toolchain.sh`, same approach as libthunder. Odin is pre-1.0 so the pin matters.
- **License**: AGPL-3.0-or-later, matching the owner's other projects.
- **Process model**: one-shot CLI, no daemon. The editor spawns kroken as a background job, feeds the selection, and pastes stdout over the selection. Parallelism is free. Writing to the file on disk was rejected because it would fight unsaved edits in the buffer.
- **Backend**: `claude -p` only. It already loads the `CLAUDE.md` hierarchy from its working directory upward (verified against the Claude Code memory docs), so kroken sets cwd to the target file's directory and does not inject `CLAUDE.md` content itself. `--bare` must never be passed for that reason.
- **Model tool access default**: read-only (`Read`, `Grep`, `Glob`) with `--add-dir` pointing at the git root. Configurable.
- **Subscriptions**: named profiles in TOML carrying env vars and extra `claude` flags. Only the owner's Max subscription exists today, so the shipped examples show one profile plus a commented alternative.
- **Config format and layering**: TOML with a hand-written subset parser (no TOML package in Odin's core library, and no third-party dependencies wanted). XDG locations plus clang-format style `.kroken` discovery, closest file wins, then a profile overlay.
- **Output extraction**: `--output-format json --json-schema` so the replacement arrives as a clean JSON string instead of prose that needs fence stripping.
- **Prompt transport**: written to a file that becomes the child's stdin. Positional arguments were rejected because of the 128 KiB per-argument limit on Linux and because the selection would show up in process listings.
- **Sessions**: not persisted by default to avoid piling up transcripts under `~/.claude/projects`.
- **Local builds on vaio**: allowed for this project. A CLI this size compiles in seconds, which the "no heavy builds on vaio" rule was never about.

## Findings from the first live run

Tags: #verification #claude

- `claude -p` with no positional prompt reads the whole prompt from stdin when stdin is a regular file, not only from a pipe. The prompt file approach therefore works as designed.
- `--json-schema` together with read-only tools works: the model read the file, then answered in the structured shape. `structured_output.replacement` mirrored the selection's trailing newline.
- The fixture's `CLAUDE.md` (Allman braces, 4-space indent, a mandated variable name) was honoured with cwd set to the file's directory and no explicit injection.
- Cost reporting in `result.json` is a client-side estimate (`total_cost_usd` about $0.18 for a 2-turn Sonnet run at low effort). On a subscription it is informational only.
- Wall time was 4.6 s end to end, of which the Claude Code process startup is a noticeable share; the run itself reported 2.1 s.
